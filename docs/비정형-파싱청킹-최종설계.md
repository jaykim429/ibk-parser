# 비정형 문서 파싱·청킹 — 최종 설계 확정서 (재검토 반영)

> 생성: 설계 워크플로(4철학 제안→비평→종합) → **재검토 워크플로(코드 독립검증 7건 + 적대 스트레스 4각도)**로 전제 정정 후 확정.
> 기준일 2026-06-29 · 브랜치 ibk-poc

---

확정. 두 핵심 사실:

1. **expandContext 런타임 호출 0건** — 설계 D항의 "섹션 본문을 judge에 전달" 배관이 실제로 끊겨 있다. 스트레스 주장 확인.

2. **입력측 TOC 방어선이 이미 존재** — `server.ts:192-213`이 쿼리 구성 시점에 점선리더+페이지번호를 이미 제거한다. 따라서 스트레스가 우려한 "입력측 TOC 누출로 인한 query false-negative"는 부분적으로 기존 방어선이 있으나, 이 정제는 `fallbackText` 경로에만 적용되고 blocks 정규화가 추가되면 비대칭이 생길 수 있다.

모든 핵심 코드 사실을 확인했다. 검증 결과 + 스트레스 결과를 종합해 최종 설계를 확정한다.

## 2. 스트레스에서 깨진 결정 — 수정/강등/기각

| 결정 | 판정 | 조치 |
|---|---|---|
| 인접 동일헤딩 병합 = P0 무위험 | **수정** | mergeLabelGroups **이후**로 이동하거나, 병합을 "동일 텍스트 AND 동일 level AND 사이 본문유닛 0개"로 한정. 골든 단위테스트(조 제목/본문 2-heading 분리 케이스)로 불변식 고정 |
| TOC 보존격리 = P0 무위험 | **수정·강등** | (a) blocks에 점선 남는지 **1샘플 dump 선검증** (markdown은 `doc-text.ts:28`에서 이미 접힘, blocks 미검증) (b) "본문 첫 유닛은 절대 (목차) 흡수 금지" 코드 가드 (c) 격리후보 leaf가 `HEADING_JO` 매칭(=목차행이 조 제목)이면 **격리 보류** (d) 임계는 문서내 분포가 아닌 "점선+페이지번호 동시성립" 결합조건 |
| section_path BM25 색인 가중 | **강등(P1→관찰)** | 무가중 도입은 장 제목 df 급증→idf 희석 회귀 가능. **가중치를 명시 config로 노출 + before/after recall ablation 후에만** 채택 |
| D항: expandContext로 judge에 섹션전문 전달 | **기각** | 런타임 호출 0건으로 배관 부재 확인. 별도 배관 구현은 본 설계 범위 밖(retrieval가 ManualChunk 미조회라는 사실①과 정합). judge 개선은 후보 content 경로 내에서만 |
| pinpoint가 coverage evidence를 "문장"으로 좁힘 | **수정** | 분산규율 내규의 false 부재 유발. **assessCoverage evidence 단위는 "조문" 유지**. pinpoint는 `judge.ts` candidateBlock 표시·judgeMatches 출력에만 추가 |
| 측정: judge 결과 diff=0 | **기각** | LLM 비결정성으로 flaky. 결정론 레이어만 diff=0, LLM 레이어는 k회 반복 라벨안정성≥0.8 |
| 측정: noise 후보 비율 하락을 합격기준 | **강등(관찰지표)** | 목적·총칙·정의 조항이 쟁점인 케이스에서 recall 깎을 유인. 게이트에서 제외, 관찰만 |

## 4. 현실적 측정안 (정답셋 확보 방법 포함)

**측정 인프라를 P0의 선행조건으로 승격** — 코드 한 줄 바꾸기 전에 러너부터.

| 레이어 | 게이트 | 산출 방법 |
|---|---|---|
| 결정론 (청크수·BM25랭킹·headingPath·keyOf) | **diff=0** | 정규화 OFF/ON 바이트 비교. 대조군 = **조문형 규정전문을 실제 manualToChunks 통과시킨 산출**(RDB 기존조문 아님 — T5) |
| LLM (judge·rerank·coverage) | **라벨 안정성 ≥0.8** | 동일입력 k회 반복 다수결/분산. diff=0 적용❌ |
| Retrieval recall | **누락 0 게이트**(개선 주장❌) | 정답셋 = **내규ID + 조문명/본문 텍스트앵커**(regId,jo❌ — jo 시프트 불변). 매뉴얼형 **8~10건 이상 확보 전엔 회귀게이트로만** 운영 |
| 추출완전성 (신규) | 페이지당 글자수 하한 미달 페이지 비율 | OCR 미발동·cand>20 스킵·부분추출을 KPI화 |
| pinpoint | 자동 대용지표 | 인용 span이 정답조항 본문에 substring 또는 임베딩유사도≥임계 포함. 사람평가 "추세"❌ |
| 과도기 (신규) | 재인덱싱 토큰불일치·부분실패 jo불일치 | 정적 before/after로는 못 잡음 |

**정답셋 생성**: 컴플라이언스 담당 수작업 라벨링. "관련"의 정의(조 단위)·주체·표본출처를 문서에 명문화. 비용 미정 항목이므로 **표본 충분 전 "개선" 주장 금지, 회귀 0만 보증**.

**상류 FN 우선 측정**: `parse-document.ts:227` cand>20 스킵·needsOcr 무음통과·`pipeline.ts:99` minBodyChars=300(전량실패만 차단, 부분추출 통과)이 **헤딩개선 recall 이득을 압도할 수 있다**. false-negative 최우선 경계 원칙상 이 상류 누락부터 측정.

## 5. PDF 파싱·청킹 LLM 도입(추후) 판단

검증 결과 위에서: **전역 도입 반대, 인덱싱 경로 한정·옵트인이 유일한 타당안**이다. 근거는 코드로 확증된다 — parseDocument는 라이브 입력분석(`pipeline.ts:77`)과 내규 인덱싱(`manual-chunk.ts:156`)이 **단일 함수를 공유**(C7)하므로, parseDocument에 무조건 LLM 정규화를 넣으면 매 사용자 요청마다 LLM이 호출돼 비용·지연이 라이브 경로로 전가된다(코드확증). 반면 demoteProseHeadings는 순수 정규식 분류기라 이 비용이 없다. 따라서 LLM 파싱/청킹은 (a)`manualToChunks` 인덱싱 1회 경로에 격리하고 (b)옵트인 플래그로 묶으며 (c)인메모리 싱글톤 캐시(`bm25-local.ts:18`) 특성상 결과가 영속화되므로 **결정론적 안정키(P1-1)와 stale 청소(P1-2)가 선결**돼야 재인덱싱 멱등성과 jo 시프트 면역이 생긴다. 더 근본적으로, 현 137 코퍼스는 이미 깨끗한 조문 구조(C6)라 LLM 파싱의 실효 대상은 "향후 들어올 비정형 매뉴얼/지침"뿐이며, **그것이 실제로 적재되기 전까지 LLM 도입은 측정 대상(before)이 없는 선투자**다. 우선순위는 P0/P1(정규식·식별자안정화)로 비정형 적재 배관을 먼저 견고히 한 뒤, 대표 매뉴얼 baseline에서 정규식 정규화가 측정노이즈에 묻히는 것이 확인될 때 비로소 P2 LLM 복원을 ablation 근거와 함께 도입하는 것이 옳다.
