# 입력 문서 파싱 → 청킹 프로세스 (상세)

업로드된 규제변동 문서(법률안·시행령·고시·보도자료·비조치의견서 등)가
**파일 버퍼 → 텍스트 → 검색 쿼리(청크)** 로 변환되는 전 과정을 다룬다.

> ⚠️ 여기서 말하는 "청킹"은 **입력 문서**를 쪼개는 것이다.
> 내규(Qdrant 적재)는 별도 오프라인 청킹(`scripts/index-regulations.mjs`, 조 단위 + 겹침 윈도우)이며 이 문서 범위 밖이다.

---

## 0. 전체 흐름

```text
업로드 버퍼
  │
  ├─[1] 파싱 (kordoc, 로컬)            lib/parse-document.ts
  │      hwp/hwpx/pdf/docx/xls → Markdown
  │      (스캔 PDF면 DGX VLM OCR 폴백) → normalizeMarkdown → pickTitle
  │
  ├─[2] 문서 유형/성격 판별            lib/server.ts
  │      detectItemType  : bill | policy
  │      detectDocNature : 규범 | 정보성
  │
  ├─[3] 구조 분석 (병렬, 서버 RO)       lib/server.ts
  │      analyzeDocument  → Analysis(키워드/개념/변경단위)
  │      parseBill        → provisions[] (조문 구조)
  │
  ├─[4] ★청킹 = 쿼리화★               lib/server.ts
  │      buildCanonicalQuery → 대표 쿼리 1개 (키워드·개념 밀도형)
  │      buildSubQueries     → 변경 단위별 서브쿼리 N개 (최대 6)
  │      queries = [canonical, ...subQueries]
  │
  └─[5] 멀티쿼리 하이브리드 검색        lib/retrieval.ts
         retrieveMany(queries)
           각 쿼리: BM25 ∥ 벡터 → RRF 융합(rawRetrieve)
           쿼리 간: cross-RRF(score 합산) → topK → 원문 보강
```

오케스트레이션 본체: [lib/pipeline.ts](../lib/pipeline.ts#L43-L83) `CompliancePipeline.run()`

## 1. 파싱 — 파일 → Markdown

파일: [lib/parse-document.ts](../lib/parse-document.ts)

### 1.1 kordoc 로딩 (폐쇄망 안전)
kordoc은 ESM 전용 + 네이티브 의존성(sharp/pdfium)을 가져 webpack 번들링과 충돌한다.
→ `new Function("s","return import(s)")` 로 **webpack 정적분석을 우회**한 런타임 동적 import.

```ts
const _dynamicImport = new Function("s", "return import(s)");
async function loadKordoc() { if (!_kordoc) _kordoc = await _dynamicImport("kordoc"); return _kordoc; }
```

### 1.2 파싱 + OCR 폴백
- 지원: `hwp3 / hwp / hwpx / hwpml / pdf / xls / xlsx / docx`
- **텍스트 PDF**: 그대로 추출 (OCR 호출 안 함)
- **스캔(이미지) PDF**: kordoc이 자동으로 **DGX Spark VLM(gemma)** OCR로 라우팅

```ts
const ocr = createVlmOcrProvider({ endpoint: `${DGX_URL}/v1/chat/completions`, model: DGX_MODEL });
const result = await parse(buffer, { ocr, removeHeaderFooter: true });
```

- `removeHeaderFooter: true` — 머리말/꼬리말 제거
- 실패 코드는 한글 메시지로 매핑(`ERROR_MESSAGES`: 암호화/DRM/손상/이미지PDF/빈 본문 등)
- `usedOcr` = warning에 `OCR_FALLBACK` 있거나 `isImageBased`

### 1.3 정규화 — `normalizeMarkdown`
파일: [lib/doc-text.ts:18](../lib/doc-text.ts#L18) (순수 함수, I/O 없음 → 단위테스트 대상)

본문은 보존하고 **정형 노이즈만** 제거:

| 처리 | 대상 |
|---|---|
| CRLF → LF | 줄바꿈 통일 |
| 행 끝 공백 제거 | `[ \t]+\n` |
| 빈 표 행 제거 | `\|  \|  \|` |
| 페이지 번호 제거 | `- 1 -` 류 |
| 의안/공고 머리말 제거 | `BOILERPLATE_LABEL`(의안번호/제출연월일/발의자/소관위원회 …) |
| 과다 개행 축약 | `\n{3,}` → `\n\n` |

### 1.4 제목 추출 — `pickTitle`
우선순위: **본문 상단 제목 패턴 > 메타데이터 제목 > 정리된 파일명**

- `titleFromContent`: 상단 30줄에서 선행 기호/번호 정리 → 본문 항목(`제N조`, `1)`, `①`)은 제외 → `TITLE_END`(…법률안/개정안/시행령/고시안/의견서/회신/해석/보도자료…) 종결 패턴이면 채택
- 없으면 `cleanFilename`(확장자/날짜코드 접두/선행 `[..]`/밑줄 정리)

**산출물** `ParsedDoc`: `{ markdown, fileType, pageCount, isImageBased, usedOcr, title, warnings }`

## 2. 문서 유형 / 성격 판별

파일: [lib/server.ts:268-298](../lib/server.ts#L268-L298)

규제변동 문서는 종류에 따라 **분석 호출 모드**와 **보고서 워딩 강도**가 달라야 한다.
하드코딩(특정 법령명 분기) 없이 **한국 공문서 보편 패턴**으로만 판별한다.

### 2.1 `detectItemType` → `bill` | `policy`
- 파일명에 `법률안/법안/의안/개정법률안` → **bill**
- (파일명+본문 3000자)에 `입법예고/시행령/시행규칙/개정고시/규정변경예고/일부개정령/행정규칙` → **policy**
- 기본 → bill
- 용도: `parseBill(is_policy=…)`, 리랭커·판정·보고서의 톤 결정

### 2.2 `detectDocNature` → `규범` | `정보성`
- `INFORMATIONAL_DOC`(보도자료/설명자료/유권해석/질의회신/비조치의견서/FAQ/카드뉴스 …) 신호가 있고
  `NORMATIVE_DOC`(법률안/시행령/고시안/입법예고/개정안/대통령령 …) 신호가 **없으면** → **정보성**
- 그 외 → **규범**
- 정보성이면 `infoOnly=true` → 판정에서 영향도 상한(모니터링 대상), 보고서가 **단정 표현을 피함**

> 정보성 자료는 그 자체로 개정 의무가 없으므로 "동향 모니터링" 관점으로 다룬다.

## 3. 구조 분석 (병렬, 서버 읽기전용)

파일: [lib/pipeline.ts:59-70](../lib/pipeline.ts#L59-L70) · [lib/server.ts:73-97](../lib/server.ts#L73-L97)

`analyze`와 `parseBill`을 **동시 호출**(`Promise.allSettled`)하여 한쪽 실패에도 진행:

```ts
const [analyzeRes, parseRes] = await Promise.allSettled([
  analyzeDocument({ lawName, documentText: doc.markdown, itemType }),  // → Analysis
  parseBill({ billId, billName, billText: doc.markdown, isPolicy }),   // → provisions[]
]);
```

- 두 호출 모두 본문을 **60,000자로 절단**(`document_text.slice(0, 60000)`)
- `analyzeDocument` 산출 `Analysis`: `law_name, law_domain, core_summary, search_keywords[], semantic_concepts[], change_overview[], provision_changes[]`
- `parseBill` 산출: `provisions[]`(조문 구조; 필드명이 문서마다 제각각)
- `lawName = analysis.law_name || 제목` 으로 확정

이 단계의 결과(정규화된 키워드/개념/변경단위)가 **청킹의 입력**이 된다.

## 4. ★ 청킹 = 쿼리화 ★

파일: [lib/server.ts:155-266](../lib/server.ts#L155-L266) · 호출 [lib/pipeline.ts:74-76](../lib/pipeline.ts#L74-L76)

### 왜 "문자수 슬라이딩"이 아니라 "쿼리화"인가
> 핵심 제약(실측): match/벡터 검색에 **긴 원문을 그대로 넣으면 임베딩이 희석되어 후보가 거의 안 나온다.**
> (원문 8000자 → 0건, 키워드 위주 짧은 쿼리 → 11건)

그래서 입력 문서 청킹은 **본문을 N자씩 자르는 방식이 아니라,
analyze가 정규화한 의미 단위(키워드/개념/변경점)를 "짧고 밀도 높은 쿼리"로 만드는 방식**이다.

```ts
const query      = buildCanonicalQuery(analysis, provisions, doc.markdown); // 대표 1
const subQueries = buildSubQueries(analysis, provisions);                   // 변경단위 N (≤6)
const queries    = [query, ...subQueries];
```

### 4.1 `buildCanonicalQuery` — 대표 쿼리 1개
[lib/server.ts:231](../lib/server.ts#L231)

- `head = law_name + law_domain`
- `terms = search_keywords + semantic_concepts` → 중복 제거 → **최대 30개**
- `q = "{head} {term1, term2, …}"` → **800자로 절단**
- 키워드가 비면 `core_summary`(≤300자)로, analyze 자체가 실패하면 ↓ 폴백

### 4.2 `buildFallbackQuery` — analyze 실패 시
[lib/server.ts:155](../lib/server.ts#L155)

원문 앞부분을 그대로 쓰면 **의안 표 마크다운 노이즈**가 들어가 검색이 망가진다. 그래서:
1. `provisions`에서 문자열 값(`content/text/title/name …`) 수집(≤600자)
2. 원문에서 표 행(`|…|`)·구분선·HTML·헤딩 마크업 제거
3. `제안이유 / 주요내용 / 개정이유` 이후 본문 우선 추출(≤800자)
4. `provText + core` → 800자

### 4.3 `buildSubQueries` — 변경 단위별 서브쿼리 (입력 문서 청킹의 본질)
[lib/server.ts:201](../lib/server.ts#L201)

긴 문서에 **변경점이 여러 개**면 단일 쿼리로 다 못 잡는다 → 변경 단위마다 쿼리 1개:

```ts
const units = analysis?.provision_changes?.length ? analysis.provision_changes
            : analysis?.change_overview?.length   ? analysis.change_overview
            : provisions ?? [];
for (const u of units) {
  const body = objText(u).replace(/\s+/g, " ").trim();   // 객체의 문자열 값만 모음
  if (body.length < 8) continue;
  const q = `${head} ${body}`.slice(0, 280);             // head=법령명+분야
  // 앞 60자 prefix로 중복 제거, 최대 6개
}
```

| 항목 | 값 |
|---|---|
| 단위 우선순위 | `provision_changes` > `change_overview` > `provisions` |
| head | `law_name + law_domain` |
| 쿼리 길이 | ≤ 280자 |
| 중복 제거 | 앞 60자 prefix |
| 최대 개수 | **6** (`maxQueries`) |

> 즉 **1개 입력 문서 → 최대 7개 쿼리**(대표 1 + 서브 6). 이게 입력 문서의 "청크"다.

## 5. 멀티쿼리 하이브리드 검색 + 융합

파일: [lib/retrieval.ts](../lib/retrieval.ts) · 호출 [lib/pipeline.ts:83](../lib/pipeline.ts#L83)

```ts
const candidates = await this.retriever.retrieveMany(queries);
```

### 5.1 단일 쿼리: `rawRetrieve` (BM25 ∥ 벡터 → RRF)
[lib/retrieval.ts:62](../lib/retrieval.ts#L62)

```ts
const [vec, bmHits] = await Promise.all([
  vectorSearch(query, vectorTopK),   // Qdrant 코사인, 4096d Qwen3
  bm25Search(query, bm25TopK),       // 로컬 한국어 bigram BM25
]);
return this.fuse(vec, bm);           // RRF
```

**RRF 융합** `fuse` [lib/retrieval.ts:38](../lib/retrieval.ts#L38):
`score(d) = Σ 1/(rrfK + rank_i(d))` — 두 리스트 모두에 걸리면 `match_source="hybrid"`, 상위 `fuseTopK`만.

### 5.2 쿼리 간: `retrieveMany` (cross-RRF)
[lib/retrieval.ts:86](../lib/retrieval.ts#L86)

- 쿼리 1개면 그냥 `retrieve`
- 여러 개면: 각 쿼리의 `rawRetrieve` 결과를 **키(내규·조) 기준으로 `final_score` 합산** → 정렬 → `fuseTopK` → 원문 보강(`enrichWithSource`)

```ts
for (const list of lists) for (const c of list) {
  score.set(k, (score.get(k) ?? 0) + (c.final_score ?? 0));  // 여러 변경점에 공통 매칭 → 가점
}
```

> 여러 변경점에서 공통으로 걸리는 내규는 가점 → **문서 전체 변경을 빠짐없이 커버.**

### 5.3 이후 (참고)
검색 후 파이프라인: **리랭크(LLM 크로스인코더) → 적합성·영향도 판정(LLM) → 보고서 생성**.
(이 문서 범위 밖)

## 7. 설계 원칙

- **하드코딩 금지**: 특정 내규/법령 분기 없음. 모든 판별은 한국 공문서 보편 패턴(정규식) + LLM 일반 판단.
- **읽기 전용**: 서버 DB에 쓰기 없음(analyze/parse/match RO + stateless 생성).
- **폐쇄망 안전**: kordoc 내재화, 폰트 self-host. 단 임베딩 엔드포인트만 외부 기본값 → 사내로 교체 필요.
- **모듈화**: 파싱(parse-document)·판별/쿼리(server)·검색(retrieval)·순수유틸(doc-text) 분리. route는 얇은 래퍼.

## 8. 개선 이력 (v15 — 논리/기능 허점 수정)

코드 리뷰에서 발견한 허점을 심각도 순으로 수정. (cacheVersion `v14→v15`, 캐시키에 튜닝 시그니처 포함 → config 변경 시 자동 무효화)

| # | 허점 | 수정 | 위치 |
|---|---|---|---|
| 1 | 서브쿼리 dedup이 `head` prefix 때문에 1개로 붕괴 | dedup 키를 **body 기준**으로 변경 | `server.ts buildSubQueries` |
| 2 | `objText`가 1-depth 문자열만 수집(중첩 변경내용 유실) | **재귀 평탄화**(배열/객체, depth≤4) | `server.ts objText` |
| 3 | 본문 60k 무경고 절단 | `config.maxAnalyzeChars` + **절단 경고** meta/log | `server.ts`·`pipeline.ts` |
| 4 | 서브쿼리6/키워드30 캡이 silent | **드롭 개수 log** | `server.ts` |
| 5 | 법안 다루는 보도자료→규범 오분류(단정 워딩) | **전달형식(보도자료 등) 우선** / 해석형식(의견서)은 규범신호 없을 때만 | `server.ts detectDocNature` |
| 6 | 규정/고시/지침 단독→bill 오라우팅 | **파일명 규정류→policy** (법안신호 우선) | `server.ts detectItemType` |
| 7 | cross-RRF가 점수합산(스케일 편향) | **rank 기반 cross-RRF** + canonical 가중치 옵션 | `retrieval.ts retrieveMany` |
| 8 | 멀티청크 조문 RRF 과대계상 | **조 단위 collapse 후 RRF** | `retrieval.ts fuse` |
| 9 | 폴백이 법안 구조(제안이유/주요내용) 가정 | 개정사유/추진배경/골자/개요/신구조문 등 **확장** | `server.ts buildFallbackQuery` |
| 10 | 시행일이 머리말 제거로 유실 | BOILERPLATE에서 **`시행 연월일` 제외(보존)** | `doc-text.ts` |
| 11 | 깨진 텍스트층 PDF 무음 통과 | **품질 게이트**(페이지당 글자/깨짐 감지→경고) | `parse-document.ts assessQuality` |
| 12 | 전 쿼리 공백→`retrieve("")` 노이즈 | **빈 쿼리 가드** | `retrieval.ts` |
| 14 | 캐시키가 fileHash+수동버전뿐 | **튜닝 시그니처 포함**(자동 무효화) | `pipeline.ts` |
| 15 | `body.length<8`로 짧은 변경 탈락 + 매직넘버 | `config.subQueryMinLen`(기본 4) + 임계값 **config화** | `server.ts`·`match-local.ts` |

## 9. 개선 이력 (v16 — 근거법령 앵커 M1)

매칭 정확도 개선: 입력 문서는 '이름이 명확한 특정 법령'이고 내규는 각자 **근거법령**을 가지므로,
그 관계를 검색 신호로 직접 사용한다(기존엔 LLM 프롬프트 텍스트로만 노출).

- `baseLawName()`로 법령명 정규화(시행령/개정표지 제거) 후 **완전 일치** 비교(부분일치 오앵커 방지: 은행법 ≠ 중소기업은행법).
- 입력 법령 = 내규 근거법령인 조문: 의미검색에 있으면 **가점**(`anchorBonus`), 누락이면 **상한 내 주입**(`anchorMax`, 리콜). 소프트 — 하드필터 아님.
- 위치: [retrieval.ts](../lib/retrieval.ts) `anchorCandidates`/`applyAnchor`, `pipeline.ts`에서 `retrieveMany(queries, lawName)`. env `ANCHOR_ENABLED/ANCHOR_BONUS/ANCHOR_MAX`.

**검증(A/B, 전자금융거래법 시행령 샘플)**: 근거법령=전자금융거래법 내규가 top-30에서 **3→6건**, top-12에서 **2→6건**으로 상승. top은 검색근거 있는 후보만(플러딩 없음), OFF는 30건 정상. 파서 단위테스트 **55/55**, 종단 파이프라인 success.

> 다음 후보(미적용): P1 신구조문대비표 전용 파싱 · M2 Qwen3 쿼리 instruction · M3 자연어 canonical 쿼리 · M7 전용 리랭커.

## 10. 개선 이력 (v18 — 도메인 게이트 + 보고서 계층화)

### 도메인 관련성 게이트 (오탐 차단)
검색은 무조건 최근접 top-K를 반환해 **무관 문서(예: 청년센터 성과코칭)도 내규에 매칭**되는 문제가 있었다.
→ 매칭 **전에** 1차 분류기([server.ts](../lib/server.ts) `assessRelevance`, 일반 LLM 판단·하드코딩 없음)로
은행·금융 규제와 무관한 문서를 차단하고 `buildOffDomainReport`로 "분석 대상 아님" 보고.
- analyze/parseBill과 **병렬** 실행(추가 지연 없음), 실패 시 fail-open, '애매하면 관련'(경계 은행주제 과차단 방지).
- env `RELEVANCE_GATE_ENABLED`. **검증**: 강서청년센터 코칭·사내 체육대회=차단, 전자금융 시행령·예금자보호 보도자료=통과.

### 보고서 계층 구조화 (가/나/다)
섹션 번호(1/1.1/2.2.1)·표는 코드가 고정, 그 아래 **항목은 AI가 깊이를 인식**해 중첩 출력 →
코드가 깊이별 한국식 마커(`가/나/다` → `1)2)3)` → `①②③`)를 결정적 부여([report.ts](../lib/report.ts) `renderOutline`).
웹은 CSS로 기본 불릿 숨김. **검증**: 실제 보고서에서 1.1 아래 `가./나.` + 중첩 `1)/2)` 정상 렌더.
