# 비정형 문서 파싱·청킹 — 프로세스 상세와 설계 이유

> IBK 규제변동 영향분석 PoC · 운영매뉴얼·작성기준처럼 조문(제N조) 골격이 없는 비정형 문서를
> 의미 단위로 파싱·청킹해 법령·규제와 매칭하기 위한 처리 과정과, **각 단계를 그렇게 설계한 이유**.
> 모든 수치는 실측 하버스/코퍼스 기준. 관련 코드는 각 절 끝에 표기.

---

## 0. 큰 그림 — 왜 ‘두 갈래 경로’인가

같은 파서(`parseDocument`)를 쓰지만 문서가 들어오는 목적에 따라 처리가 갈립니다.

| 경로 | 들어오는 것 | 처리 | 산출 |
|---|---|---|---|
| **입력 경로** | 규제·규정·동향(분석 대상) | parse → 본문 표본화 → **의미 분절**(변경단위·의무) → 서브쿼리 | 보고서 |
| **인덱싱 경로** | 기업은행 내규(검색 대상) | parse → **헤딩 섹션 청킹**(manualToChunks) → 임베딩 | 벡터DB 색인 |

**이유.** 입력 문서는 “무엇이 바뀌었나(변경점)”를 뽑아 질의로 만드는 게 목적이고, 내규는 “어디에 그 내용이 있나”를 찾을 수 있게 잘게 색인하는 게 목적입니다. 목적이 다르므로 같은 본문이라도 다르게 다룹니다.
- 입력은 **벡터 청킹을 하지 않습니다.** 대신 LLM이 본문을 읽어 ‘변경 단위/의무’를 의미적으로 분절합니다 → 분절 품질이 곧 매칭 정확도.
- ‘청킹(고정·섹션 단위로 자르기)’의 본 무대는 **내규 인덱싱**입니다. 비정형 매뉴얼이 내규로 적재될 때 청킹 품질이 검색 재현율을 좌우합니다.

> 핵심 함의: 비정형 매뉴얼(예: CA채널 운영매뉴얼)은 *입력*이 아니라 *인덱싱 대상 내규*입니다. 헤딩 정규화 같은 청킹 개선은 **내규를 (재)인덱싱할 때** 효과가 납니다.

`lib/pipeline.ts`(입력 경로) · `scripts/index-manuals.ts`→`lib/manual-chunk.ts`(인덱싱 경로)

## 1. 파싱 — 구조 블록으로 풀기

`parseDocument(buffer, filename)`가 PDF·HWP·HWPX·DOCX·XLS·TXT를 받아 다음을 만듭니다.

- **`blocks`**: 구조 중간표현. `heading`(표제) · `paragraph`(본문) · `list`(목록) · `table`(표). 매칭·청킹·복원이 전부 이 블록을 씁니다.
- **`markdown`**: 평문 본문. 입력 경로의 분석은 이걸 씁니다.
- **품질 신호**: `lowQuality`(추출 의심) · `usedOcr` · 한글추출률 · OCR 권장 경고.

### 1-1. 헤딩 과분류 정규화 — `demoteProseHeadings`
HWP/PDF는 흔히 **본문 문장까지 전부 ‘헤딩’으로 태깅**합니다(예: 모범규준의 모든 문단이 헤딩 레벨로). 그대로 두면 청킹이 문장마다 쪼개져 ‘의미 단위’가 깨집니다.

→ **규칙(보편·하드코딩 없음):** 헤딩은 ‘짧은 표제’만 유지한다.
- `제N조/장/절` 제목 → 보존(≤55자). 단 ‘…한다/된다’ 같은 **강한 서술형 어미**면 본문으로 강등.
- 명사형 종결(…등/…사항/…경우)은 정상 조문 제목일 수 있어 **강등하지 않음**(과강등 방지).
- 그 외 길거나(>25자) 서술형/콜론정의/디코드실패(�)면 ‘문단’으로 강등.

**이유.** 특정 표제어 사전이 아니라 **‘짧은 표제 vs 서술형 문장’이라는 형태 신호**로 가릅니다. 표제어 목록을 하드코딩하면 미지의 문서에서 깨지고, 신규 표제어마다 추가해야 합니다. 형태 신호는 문서 종류와 무관하게 작동합니다. (실측: 신규 내규 54건에서 본문성 헤딩 1~138개가 문서별로 적절히 강등됨.)

`lib/parse-document.ts` — `demoteProseHeadings` / `isShortHeadingTitle`

## 2. 청킹 — 왜 고정 글자수로 안 자르나

`manualToChunks`가 blocks를 **헤딩 섹션 단위**로 묶습니다. 고정 N자 슬라이딩 윈도우를 **쓰지 않습니다.**

**이유.** 고정 글자수는 조문 한복판을 잘라 의미를 끊습니다. 비정형 문서라도 장·절·번호·표제 같은 **최소한의 계층**은 있으므로, 그 계층을 경계로 삼으면 ‘의미 단위’가 보존돼 임베딩 검색 재현율이 올라갑니다.

### 2-1. 헤딩 섹션 묶음 — `blocksToUnits`
헤딩이 바뀔 때까지의 본문을 한 섹션으로 묶고 `headingPath`(예: `제2장 > 제5조`)를 부여합니다. **헤딩 텍스트 자체도 본문으로 방출**합니다.
- *이유:* 조문이 heading으로만 분류되면 그 텍스트가 본문에서 사라져 “제5조” 같은 핵심 라벨이 검색에서 누락됩니다. 헤딩도 본문으로 흘려 유실을 막습니다.

### 2-2. 표 선형화
표를 “헤더=값” 문장으로 풉니다. 예: `제정일=개정일, 2025.01.02=2025.07.01`.
- *이유:* 표를 이미지/격자로 두면 임베딩·키워드 검색이 안 됩니다. 선형화하면 표 내용도 일반 텍스트처럼 검색됩니다. (작성기준류는 본문보다 표가 더 많음 — 표를 못 다루면 핵심을 놓침.)

### 2-3. 분리된 조 제목·본문 복원 — `mergeLabelGroups`
HWP는 조 ‘제목’과 ‘본문’을 따로 헤딩으로 쪼개곤 합니다. 라벨(`제N조(…)`)만 담긴 그룹에 다음 본문 그룹을 흡수해 조 단위로 복원합니다.
- *가드:* **라벨이 곧 섹션 제목인 그룹(`prevText===prevLeaf`)·30자 이하·번호 라벨 패턴**일 때만 병합 → 일반 본문 오병합 차단.
- *이유:* 무조건 병합하면 서로 다른 조의 본문이 한 청크로 뭉쳐(과병합) 검색 단위가 비대해져 오히려 재현율이 떨어집니다(false-negative). 그래서 ‘라벨만 있는 그룹’으로 한정합니다.

### 2-4. 길이 다듬기 — `subSplit` (900자 / 150 겹침)
900자를 넘으면 150자 겹침으로 나누되 **어절·행 경계에 스냅**(끝이 단어 중간이면 가까운 줄바꿈/공백으로 당김).
- *이유(900/150):* 임베딩 모델의 의미 응집 한계와 표시 가독성의 절충값. 겹침은 경계에 걸친 문장이 양쪽 청크에서 모두 검색되게 합니다.
- *이유(표도 분할):* 예전엔 거대표를 통째로 1청크로 둬 임베딩 길이 캡(2000자)에서 **꼬리 행이 잘려 검색 불가**였습니다. 표도 행 경계(`\n`)로 나눠 꼬리손실을 없앴습니다. (실측: 신규 54건 전부 청크 ≤900, 캡초과 0.)

### 2-5. 청크 표현
임베딩/BM25 텍스트 = **섹션경로 + 본문**. 표시·확장용 `body`는 원문 그대로.
- *이유:* 섹션경로(예: `제2장 임원 > 제5조`)를 붙이면 본문만으로는 약한 맥락(어느 장/조인지)이 임베딩에 들어가 정확도가 오릅니다.

`lib/manual-chunk.ts`

## 3. 비정형 특유의 난점과 해법 — `heading-normalize`

조문형은 깨끗하지만, 운영매뉴얼류는 4가지가 반복적으로 깨집니다. 모두 **레이아웃 신호**로 식별 가능해 LLM·좌표 없이 **순수 정규식**으로 다룹니다. 적용은 **인덱싱 경로 전용**(라이브 분석은 markdown을 쓰므로 무영향).

| 난점 | 증상(실측) | 해법 | 왜 이렇게 |
|---|---|---|---|
| **목차(TOC) 누출** | 점선 리더 목차가 본문처럼 9청크로 인덱싱 | 점선+페이지번호 연속 구간을 **단일 ‘(목차)’ 메타청크로 흡수**(삭제 아님) | **삭제는 비가역** — 잘못 잡으면 본문 영구 누락(false-negative). 보존격리는 잘못 잡아도 내용이 살아있음 |
| **헤딩 단편화** | `1 배경`→`배`, `5⇥가이드`, 개행 섞인 `↵필수↵` | 탭·개행·연속공백을 단일 공백으로 접합·트림 | 형태 신호라 문서 무관·안전. (번호 분리 복원 `배`→`1 배경`은 좌표 의존이라 **보류**) |
| **인접 중복 헤딩** | 같은 제목 연달아 2번 → 섹션 갈림 | 같은 텍스트·같은 레벨·사이 본문 0개일 때만 1개로 dedup | 내용 손실 0(동일 텍스트). 사이에 본문 있으면 병합 안 함(서로 다른 섹션 보호) |
| **공백붕괴·연혁삽입** | 띄어쓰기 소실, 조문 중간 `2014.9.11 제22차개정` 삽입 | 인용 렌더 단계에서 공백 정규화+연혁 분리(향후) | 검색은 무해(BM25 2-gram이 흡수), 표시 가독성 문제라 우선순위 차등 |

### 왜 LLM을 안 쓰고 정규식인가 (가장 중요한 이유)
1. **비용·부작용 전가 방지.** `parseDocument`는 라이브 분석과 내규 인덱싱이 **공유**합니다. 여기에 LLM 정규화를 넣으면 매 사용자 요청마다 LLM이 호출돼 비용·지연이 라이브로 전가됩니다. 정규식은 이 비용이 0입니다.
2. **결정성·재현성.** 정규식은 같은 입력에 항상 같은 결과 → 재인덱싱 멱등성·회귀 테스트가 가능.
3. **미지 문서형태 견고성.** 점선·번호·공백은 매뉴얼/보고서/조문형에 공통인 보편 신호라 새 문서에도 작동.
4. **그래서 LLM은 ‘추후·인덱싱 한정·옵트인’**으로만. 현 내규는 이미 조문 구조가 깨끗해(실측 TOC 0) LLM 파싱의 실효 대상은 “향후 들어올 비정형”뿐이며, 그것이 적재되기 전엔 효과를 잴 대상조차 없습니다.

### 왜 ‘조문형 무회귀’를 보장하나
정규화는 비정형 신호(점선·중복)가 있을 때만 작동합니다. 조문형(제N조)은 그런 신호가 없어 사실상 **무동작**. 실측으로 조문형 3건의 청크 수가 정규화 전·후 **완전 불변(diff=0)**임을 확인했습니다 → 기존 품질 회귀 위험 0.

`lib/heading-normalize.ts` · 임계는 `lib/config.ts`에 외부화(`tocRunsPerBlock`·`tocMinLines`·`tocManyRuns`)

## 4. 매칭으로 흐르는 경로 — 왜 헤딩이 중요한가

청킹 산출이 검색·판정에 닿는 실제 경로는 **3가지**입니다(코드 검증 확정).

1. **키워드(BM25):** 색인 텍스트 = `내규명 + 조문명×2 + 본문`. 조문명(=headingPath 말단)을 **2배 가중**하므로, 헤딩이 깨끗할수록 키워드 정합이 살아납니다.
2. **벡터(임베딩):** 섹션경로+본문을 임베딩 → 섹션경로 복원이 곧 임베딩 품질.
3. **근거법령 앵커:** 입력 법령명과 내규 ‘근거법령’이 완전일치하면 가점·주입(텍스트 매칭과 독립한 ‘제도적 직접 관련’ 신호).
- *이유:* 의미검색(벡터)이 놓치는 ‘제도적으로 직접 연결된’ 조문을 앵커가 건집니다. 법령명 정규화가 가장 값싸게 재현율을 올리는 지점.

### 본문 완전동일 후보 접기 — `dedupeByContent`
같은 내규의 동일 본문이 다른 조문번호로 중복 적재된 경우(예: ‘점검보고서’ 본문이 제12조·제20조에 동일) 영향내규 중복행·카운트 부풀림이 생깁니다. **본문이 완전 일치(40자↑)할 때만** 상위 랭크 1건으로 접습니다.
- *이유:* 키 기반 접기(`regId|type|jo`)는 jo가 달라 못 잡습니다. 본문 해시로 보완하되, **완전 일치+40자 이상**만 접어 짧은 조의 우연 일치를 방지(보수적 → 고유 후보를 떨어뜨릴 수 없음).

`lib/bm25-local.ts` · `lib/retrieval.ts` · `lib/regulation-source.ts`

## 5. 식별자 안정화 — 재인덱싱이 안전하려면

매뉴얼 청크의 색인 식별자(jo)는 ‘일련번호(i+1)’입니다. 청킹 구성이 바뀌면(예: 목차 격리로 청크 수 변동) 번호가 밀려, **재인덱싱 시 옛 포인트가 유령으로 남아** 검색 노이즈·매칭 오류(절단본 판정)를 유발합니다.

→ **해법: stale 포인트 청소.** 재인덱싱 시 해당 내규의 기존 포인트를 **먼저 삭제 후 재적재**.
- *가드:* `source=="manual"` 필터로 한정 → **조문형 RDB 적재분은 절대 건드리지 않음.**
- *왜 jo를 해시로 안 바꿨나:* 보고서가 jo를 `제{jo}조`로 렌더하므로 해시로 바꾸면 표시가 깨집니다. 더 안전한 stale 청소로 같은 문제(유령 포인트)를 해결했습니다.

`scripts/index-manuals.ts`

## 6. 설계 원칙 종합 (왜 전반적으로 이 방향인가)

| 원칙 | 구체 | 이유 |
|---|---|---|
| **false-negative 최우선** | 관련 내규 누락이 최악(컴플라이언스 도구). 목차도 ‘삭제’ 아닌 ‘보존격리’, 병합·dedup은 손실 0일 때만 | 잘못 빠뜨린 규제는 사람이 영영 못 봄. 노이즈(가짜 양성)는 사람이 거르지만 누락은 못 거름 |
| **오버피팅·하드코딩 배제** | 특정 파일·표제어 분기 없음. 형태/레이아웃 신호로만 판단 | 보편 적용·미지형태 견고. 케이스 분기는 늘 새 케이스에서 깨짐 |
| **모듈화·외부화** | 임계값 전부 config(env)로, 정규화는 단일 모듈 | 코퍼스 따라 튜닝 가능, 다른 앱 이식 시 env만 교체 |
| **검증 가능성** | 결정론 레이어는 diff=0 게이트, LLM 레이어는 반복 안정성으로 분리 측정 | “개선했다”를 수치로 증명. 측정 인프라를 코드 변경의 선행조건으로 |
| **라이브 무영향 분리** | 청킹 개선은 인덱싱 경로 전용 | 매 요청 비용·부작용 전가 방지(parseDocument 공유 특성) |
